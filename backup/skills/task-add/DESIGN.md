# task-add 設計書 — カレンダー突合つきTodoist登録ゲート

作成日: 2026-08-03 ／ 対象: 草川たくや 議員業務作業環境

## 1. 解く問題

Todoistへタスクを登録するとき、期限日を「今日+3日」等の既定値や勘で決めていた。その日に議会が入っていても、前後が予定で埋まっていても気づかないまま登録され、結果として期限切れタスクが積み上がる。

既存ルール `feedback_ask_destination_and_deadline_before_register`（保存先＋期限を提示→本人回答後に登録）は「聞く」ところまでは担保しているが、**提示する期限日が実施可能かどうかの裏取りが無い**。ここを埋める。

## 2. スコープ

### やること
- 期限付きタスクの新規登録時に、Google Calendar と突合して実施可能性を判定する
- 判定結果（可能／タイト／無理＋代替案）を提示し、草川の承認を得てから登録する
- 突合を飛ばした登録を hook で構造的にブロックする

### やらないこと（v1）
- 移動時間の考慮
- 既存Todoistタスクの所要時間を空き時間から差し引く精緻な負荷計算（件数表示のみ）
- 期限を「今日」に付け替える操作のゲート（朝ブリーフィングで予定を見た上での当日判断のため、突合の付加価値が無い）
- td.py へのGoogle Calendar API直接統合（認証を別途組む必要があり、MCP経由で足りる）

## 3. アーキテクチャ

3層構成。責務を分離し、hook層は「止めるだけ」・skill層は「判定と提案だけ」・登録は既存の `td.py` に委ねる。

| 層 | 実体 | 責務 | 依存 |
|---|---|---|---|
| hook層 | `~/.claude/hooks/todoist_calendar_guard.py` | 期限付き登録を検知し、突合記録が無ければ deny | `_verified.json` を読むのみ |
| skill層 | `~/.claude/skills/task-add/SKILL.md` | 所要推定→カレンダー取得→空き算出→判定→提案→承認取得→`_verified.json` 書込→`td.py add` | Google Calendar MCP, td.py |
| トリガー層 | CLAUDE.md 追記 | 入口の統一 | — |

### データフロー

```
草川「〇〇のタスク登録して」
  │
  ├─► [skill] 所要推定（既定テーブル＋推定）
  ├─► [skill] Calendar list_events（今日〜期限候補+7日を1回だけ取得）
  ├─► [skill] 日別空き時間算出 → 累積空き
  ├─► [skill] 3値判定（✅可能 / ⚠️タイト / 🚫無理＋代替2案）
  ├─► [skill] 提案を1回で提示 ────► 草川が選択
  ├─► [skill] 承認分を _verified.json に書込（TTL 30分）
  └─► [skill] td.py add 実行
         │
         └─► [hook] _verified.json を照合 → 一致すれば allow
```

## 4. 判定ロジック

### 4.1 稼働時間モデル

- 稼働帯: **全曜日 9:00–21:00**（12時間）。土日祝も同じ
- **終日予定がある日は空き 0**（議会・出張・終日イベントは作業不可日とみなす）
- 予定と予定の隙間が **30分未満のものはカウントしない**（実作業に使えないため）
- 当日は `max(9:00, 現在時刻)` から算出する

### 4.2 空き時間の算出

期限候補日まで（今日を含む）の各日について:

1. 稼働帯 9:00–21:00 を用意する
2. その日の予定を取得し、重なりをマージする
3. 終日予定が1件でもあれば、その日の空きは 0 とする
4. 稼働帯から予定を差し引き、残った区間のうち 30分以上のものだけを合計する
5. 全日の合計を **累積空き時間** とする

### 4.3 単日ではなく累積で見る理由

期限日当日が議会で埋まっていても、前日までに片付けられるなら実施可能である。単日判定では誤警告が量産され、警告そのものが無視されるようになる。したがって判定の主軸は累積空き時間とし、期限日当日の空きは補助情報（着手推奨日の算出）として使う。

### 4.4 3値判定

| 判定 | 条件 | 出力 |
|---|---|---|
| ✅ 可能 | 累積空き ≧ 想定所要 × 1.5 | 着手推奨日を併記 |
| ⚠️ タイト | 想定所要 ≦ 累積空き < 想定所要 × 1.5 | 逼迫の理由（終日予定日等）と着手推奨日を併記 |
| 🚫 無理 | 累積空き < 想定所要 | 代替期限日を2案（最短で足りる日／余裕×1.5を満たす日） |

**着手推奨日**: 「その日から期限日までの空き時間の合計が想定所要以上になる」日のうち、**最も遅い日**。つまりこれ以上先延ばしすると間に合わなくなる境界日を指す。

### 4.5 想定所要の既定テーブル

タスク内容から推定する。該当が無ければ内容から私が推定し、根拠を1行添える。**推定値は提案時に必ず表示**し、草川がその場で訂正できるようにする（訂正されたら再計算する）。

| 種別 | 判定語 | 既定所要 |
|---|---|---|
| 連絡・電話・アポ取り | 電話／連絡／アポ／確認する | 15分 |
| メール・DM返信 | 返信／メール／返事 | 30分 |
| 資料読み込み | 読む／目を通す／資料確認 | 1h |
| 挨拶原稿 | 挨拶／祝辞 | 1.5h |
| ブログ・SNS | ブログ／投稿／発信 | 2h |
| 議案分析・調査 | 分析／調査／リサーチ | 3h |
| 一般質問・議案質疑原稿 | 一般質問／質疑／通告 | 4h |
| スライド・報告会資料 | スライド／資料作成／報告会 | 4h |
| 印刷物制作・入稿 | チラシ／ポスター／リーフレット／入稿 | 8h（1日） |
| 訪問・現地確認 | 訪問／現地／視察 | 2h |

### 4.6 既存タスク負荷の扱い

同期間に期限が来る既存Todoistタスクの**件数のみ**を `td.py week` から取得して併記する（例: 「同期間に既存タスク7件」）。所要時間を推定して差し引くことはしない。精度の裏付けが無い数字で判定を歪めるより、件数という確かな情報を草川に渡して判断材料にしてもらう。

## 5. 提案フォーマット

承認を得る前に、必ずこの形で1回提示する。

```
📋 タスク登録の確認（カレンダー突合済み 8/3〜8/12・同期間の既存タスク7件）

1. 川合町報告会のスライド作成
   PJ: 🏛 議員活動 ／ 期限案: 8/12(火) ／ 想定所要: 4h
   累積空き 11h → ✅ 可能（着手推奨 8/8）

2. ◯◯さんへ回答メール
   PJ: 🏛 議員活動 ／ 期限案: 8/6(木) ／ 想定所要: 30分
   累積空き 3.5h → ⚠️ タイト（8/5終日議会・8/6は予定4件）

3. リーフレット入稿
   PJ: 🗳 選挙2026 ／ 期限案: 8/8(金) ／ 想定所要: 8h
   🚫 累積空き 6h < 所要 8h
      代替案 a) 8/13(水) 累積12h  b) 8/18(月) 累積20h ●推奨

→ 「1と2」「3はaで」「全部」「見送り」等でお答えください
```

草川の返答が無いもの・見送られたものは登録しない。

## 6. hook 仕様

### 6.1 発火条件

`PreToolUse` で以下を監視する。

| tool | ゲート対象 | 素通し |
|---|---|---|
| `Bash` | commandに `td.py add` を含み、かつ `--due` がある | `--due` 無し／`done`／`rm`／`list`／`projects`／`morning` 等 |
| `mcp__claude_ai_Todoist__add-tasks` | `dueString` または `deadlineDate` がある | 期限なし |
| `mcp__claude_ai_Todoist__reschedule-tasks` | 変更後の日付が**明日以降** | 今日への付け替え |
| `mcp__claude_ai_Todoist__update-tasks` | `dueString`/`deadlineDate` を明日以降に設定 | 期限に触れない更新 |

その他のTodoist操作（完了・削除・プロジェクト操作・検索）は一切ゲートしない。

### 6.2 突合記録 `_verified.json`

skillが承認取得後に `~/.claude/skills/task-add/_verified.json` を書く。descを汚さないためファイル方式を採る。

```json
{
  "generated_at": "2026-08-03T14:22:10+09:00",
  "ttl_minutes": 30,
  "calendar_ok": true,
  "approved": [
    {"content": "川合町報告会のスライド作成", "due": "2026-08-12", "estimate_h": 4.0, "verdict": "ok"}
  ]
}
```

### 6.3 照合ルール

hookは登録されようとしている各タスクについて次を確認する。

1. `generated_at` から `ttl_minutes` 以内であること（超過していれば無効）
2. `due` が完全一致すること
3. `content` が一致すること。表記ゆれを吸収するため、空白・記号・絵文字を除去して正規化した上で、**どちらかがもう一方を含む** か **先頭10文字が一致** すれば一致とみなす

いずれかを満たさなければ deny する。

### 6.4 deny時の差し戻しメッセージ

```
カレンダー突合が未実施です。task-add スキルを起動し、
期限日の実施可能性を判定した上で草川の承認を得てください。
（突合不要な場合は期限を外して登録するか、草川に直接確認してください）
```

hookは `permissionDecision: "deny"` と `permissionDecisionReason` を返す。実装時に Claude Code の PreToolUse hook 出力契約を公式ドキュメントで確認してから確定する。

### 6.5 フェイルセーフ

業務が止まることを防ぐため、以下は**通す**。

- Google Calendar MCP が応答しない場合: skillが `calendar_ok: false` で記録を書き、hookは通す。ただし提案・登録時に「⚠️ カレンダー未確認で登録」と明示する
- `_verified.json` が存在しない・壊れている場合: **deny する**（フェイルクローズ）。未突合なのだから止めるのが正しく、素通しすると仕組みが空洞化する
- hookスクリプト自体が例外で落ちた場合: exit 0 で通す（hookのバグで登録が全面停止する事態を避ける）

## 10. 受け入れ条件

1. `td.py add "テスト" --due 2026-08-10` を突合なしで直接叩くと hook が deny する
2. task-add スキルを通して同じタスクを登録すると成功する
3. 期限なしの `td.py add "テスト"` は hook を素通しする
4. `td.py done <id>` `td.py list` `td.py morning` は素通しする
5. 終日予定のある日を期限にすると、その日の空きが 0 として計上される
6. 累積空きが所要を下回るとき、代替期限日が2案提示される
7. `_verified.json` の TTL 超過後に同じ登録を試みると deny される
8. 既存の Stop hook（sync-to-git.sh）が壊れていない
