# task-add 設計書 — カレンダー突合つきTodoist登録ゲート

作成日: 2026-08-03 ／ 対象: 草川たくや 議員業務作業環境

## 1. 解く問題

Todoistへタスクを登録するとき、期限日を「今日+3日」等の既定値や勘で決めていた。その日に議会が入っていても、前後が予定で埋まっていても気づかないまま登録され、結果として期限切れタスクが積み上がる。

既存ルール `feedback_ask_destination_and_deadline_before_register`（保存先＋期限を提示→本人回答後に登録）は「聞く」ところまでは担保しているが、**提示する期限日が実施可能かどうかの裏取りが無い**。ここを埋める。

## 2. スコープ

### やること
- 期限付きタスクの新規登録時に、Google Calendar と突合して実施可能性を判定する
- 判定結果（可能／タイト／無理＋代替案）を提示し、草川の承認を得てから登録する
- 突合を飛ばした登録を hook で構造的にブロックする

### やらないこと（v1）
- 移動時間の考慮
- 既存Todoistタスクの所要時間を空き時間から差し引く精緻な負荷計算（件数表示のみ）
- 期限を「今日」に付け替える操作のゲート（朝ブリーフィングで予定を見た上での当日判断のため、突合の付加価値が無い）
- td.py へのGoogle Calendar API直接統合（認証を別途組む必要があり、MCP経由で足りる）

## 3. アーキテクチャ

3層構成。責務を分離し、hook層は「止めるだけ」・skill層は「判定と提案だけ」・登録は既存の `td.py` に委ねる。

| 層 | 実体 | 責務 | 依存 |
|---|---|---|---|
| hook層 | `~/.claude/hooks/todoist_calendar_guard.py` | 期限付き登録を検知し、突合記録が無ければ deny | `_verified.json` を読むのみ |
| skill層 | `~/.claude/skills/task-add/SKILL.md` | 所要推定→カレンダー取得→空き算出→判定→提案→承認取得→`_verified.json` 書込→`td.py add` | Google Calendar MCP, td.py |
| トリガー層 | CLAUDE.md 追記 | 入口の統一 | — |

### データフロー

```
草川「〇〇のタスク登録して」
  │
  ├─► [skill] 所要推定（既定テーブル＋推定）
  ├─► [skill] Calendar list_events（今日〜期限候補+7日を1回だけ取得）
  ├─► [skill] 日別空き時間算出 → 累積空き
  ├─► [skill] 3値判定（✅可能 / ⚠️タイト / 🚫無理＋代替2案）
  ├─► [skill] 提案を1回で提示 ────► 草川が選択
  ├─► [skill] 承認分を _verified.json に書込（TTL 30分）
  └─► [skill] td.py add 実行
         │
         └─► [hook] _verified.json を照合 → 一致すれば allow
```

## 4. 判定ロジック

### 4.1 稼働時間モデル

- 稼働帯: **全曜日 9:00–21:00**（12時間）。土日祝も同じ
- **終日予定がある日は作業不可日**（議会・出張・終日イベント）
- 予定と予定の隙間が **30分未満のものはカウントしない**（実作業に使えないため）
- 当日は `max(9:00, 現在時刻)` から算出する
- 移動時間は考慮しない（v1）

### 4.2 セッションモデル

**所要時間を「累積時間」ではなく「1時間セッションの回数」で数える。**

4時間かかる原稿は、4時間の空きがある1日で片付くものではない。議員の1日は細切れであり、実際には数日に分けて1時間ずつ進める。累積時間で判定すると「累積8hあるから入稿は間に合う」という現実離れした判定が出る。

- **1セッション = 1時間の連続した空き**
- 30分以下の軽いタスクは **30分枠×1** として扱う
- **1日に同一タスクへ割けるのは最大2セッション**。同じ案件に3時間以上を連続で充てられる日は実際にはほぼ無いため

### 4.3 空き枠の算出

期限候補日まで（今日を含む）の各日について:

1. 稼働帯 9:00–21:00 を用意する
2. その日の予定を取得し、重なりをマージする
3. 終日予定が1件でもあれば、その日の確保可能セッションは 0 とする
4. 稼働帯から予定を差し引き、残った連続区間を出す
5. その日の確保可能セッション数 = `min(2, 1時間以上の連続区間の合計時間の切り捨て)`
6. 全日の合計を **確保可能セッション数** とする

当日は `max(9:00, 現在時刻)` から算出する。30分未満の隙間はカウントしない。

### 4.4 3値判定

| 判定 | 条件 | 出力 |
|---|---|---|
| ✅ 可能 | 確保可能 ≧ 必要セッション × 1.5 | 着手推奨日を併記 |
| ⚠️ タイト | 必要 ≦ 確保可能 < 必要 × 1.5 | 逼迫の理由（終日予定日等）と着手推奨日を併記 |
| 🚫 無理 | 確保可能 < 必要セッション | 代替期限日を2案（最短で足りる日／余裕×1.5を満たす日） |

**着手推奨日**: 「その日から期限日までに確保できるセッション数が必要数以上になる」日のうち、**最も遅い日**。これ以上先延ばしすると間に合わなくなる境界日を指す。

**最低所要日数** = `ceil(必要セッション数 ÷ 2)`。期限日までの残り日数がこれを下回る時点で、空き状況を見るまでもなく 🚫 とする（例: 入稿8セッションを3日後の期限で登録しようとした場合）。

### 4.5 想定所要の既定テーブル

タスク内容から推定する。該当が無ければ内容から私が推定し、根拠を1行添える。**推定値は提案時に必ず表示**し、草川がその場で訂正できるようにする（訂正されたら再計算する）。

| 種別 | 判定語 | 想定所要 | 必要セッション | 最低所要日数 |
|---|---|---|---|---|
| 連絡・電話・アポ取り | 電話／連絡／アポ／確認する | 15分 | 30分枠×1 | 1日 |
| メール・DM返信 | 返信／メール／返事 | 30分 | 30分枠×1 | 1日 |
| 挨拶原稿 | 挨拶／祝辞 | 30分 | 30分枠×1 | 1日 |
| 資料読み込み | 読む／目を通す／資料確認 | 1h | 1h×1 | 1日 |
| ブログ・SNS | ブログ／投稿／発信 | 1h | 1h×1 | 1日 |
| 訪問・現地確認 | 訪問／現地／視察 | 1h | 1h×1 | 1日 |
| 議案分析・調査 | 分析／調査／リサーチ | 3h | 1h×3 | 2日 |
| 一般質問・議案質疑原稿 | 一般質問／質疑／通告 | 4h | 1h×4 | 2日 |
| スライド・報告会資料 | スライド／資料作成／報告会 | 4h | 1h×4 | 2日 |
| 印刷物制作・入稿 | チラシ／ポスター／リーフレット／入稿 | 8h | 1h×8 | 4日 |

### 4.6 既存タスク負荷の扱い

同期間に期限が来る既存Todoistタスクの**件数のみ**を `td.py week` から取得して併記する（例: 「同期間に既存タスク7件」）。所要時間を推定して差し引くことはしない。精度の裏付けが無い数字で判定を歪めるより、件数という確かな情報を草川に渡して判断材料にしてもらう。

## 5. 提案フォーマット

承認を得る前に、必ずこの形で1回提示する。

```
📋 タスク登録の確認（カレンダー突合済み 8/3〜8/12・同期間の既存タスク7件）

1. 川合町報告会のスライド作成
   PJ: 🏛 議員活動 ／ 期限案: 8/12(火) ／ 想定: 1h×4回（最低2日）
   確保可能 9回 → ✅ 可能（着手推奨 8/8）

2. ◯◯さんへ回答メール
   PJ: 🏛 議員活動 ／ 期限案: 8/6(木) ／ 想定: 30分枠×1
   確保可能 1回 → ⚠️ タイト（8/5終日議会・8/6は予定4件）

3. リーフレット入稿
   PJ: 🗳 選挙2026 ／ 期限案: 8/8(金) ／ 想定: 1h×8回（最低4日）
   🚫 確保可能 5回 < 必要 8回
      代替案 a) 8/15(金) 確保9回  b) 8/20(水) 確保13回 ●推奨

→ 「1と2」「3はaで」「全部」「見送り」等でお答えください
```

草川の返答が無いもの・見送られたものは登録しない。

## 6. hook 仕様

### 6.1 発火条件

`PreToolUse` で以下を監視する。

| tool | ゲート対象 | 素通し |
|---|---|---|
| `Bash` | commandに `td.py add` を含み、かつ `--due` がある | `--due` 無し／`done`／`rm`／`list`／`projects`／`morning` 等 |
| `mcp__claude_ai_Todoist__add-tasks` | `dueString` または `deadlineDate` がある | 期限なし |

**新規登録（add）のみをゲートする。** 既存タスクの期限変更（`reschedule-tasks`／`update-tasks`）はゲートしない。理由は2つ。①朝の繰越は朝ブリーフィングで予定を見た上での再判断であり、突合の付加価値が小さい ②これらのtool入力にはタスクIDしか無くタスク内容が含まれないため、突合記録との照合が期限日だけの弱い一致になる。

既知の穴として「期限なしで登録してから期限変更する」経路はゲートを通らない。v1では許容する（草川の運用では発生しない経路であり、塞ぐと朝の繰越が毎回ブロックされる副作用の方が大きい）。

その他のTodoist操作（完了・削除・プロジェクト操作・検索）は一切ゲートしない。

### 6.2 突合記録 `_verified.json`

skillが承認取得後に `~/.claude/skills/task-add/_verified.json` を書く。descを汚さないためファイル方式を採る。

```json
{
  "generated_at": "2026-08-03T14:22:10+09:00",
  "ttl_minutes": 30,
  "calendar_ok": true,
  "approved": [
    {"content": "川合町報告会のスライド作成", "due": "2026-08-12", "sessions": 4, "verdict": "ok"}
  ]
}
```

### 6.3 照合ルール

hookは登録されようとしている各タスクについて次を確認する。

1. `generated_at` から `ttl_minutes` 以内であること（超過していれば無効）
2. `due` が完全一致すること
3. `content` が一致すること。表記ゆれを吸収するため、空白・記号・絵文字を除去して正規化した上で、**どちらかがもう一方を含む** か **先頭10文字が一致** すれば一致とみなす

いずれかを満たさなければ deny する。

### 6.4 deny時の差し戻しメッセージ

```
カレンダー突合が未実施です。task-add スキルを起動し、
期限日の実施可能性を判定した上で草川の承認を得てください。
（突合不要な場合は期限を外して登録するか、草川に直接確認してください）
```

hookは `permissionDecision: "deny"` と `permissionDecisionReason` を返す。実装時に Claude Code の PreToolUse hook 出力契約を公式ドキュメントで確認してから確定する。

### 6.5 フェイルセーフ

業務が止まることを防ぐため、以下は**通す**。

- Google Calendar MCP が応答しない場合: skillが `calendar_ok: false` で記録を書けば通る。hookは `calendar_ok` の値で分岐しない（記録があれば通す）。ただし skill は提案・登録時に「⚠️ カレンダー未確認で登録」と明示する
- 突合済みの場合、hookは**何も出力せず exit 0** する（`permissionDecision: "allow"` を返すと通常の許可フローを飛ばしてしまうため、判断を委ねる）
- `_verified.json` が存在しない・壊れている場合: **deny する**（フェイルクローズ）。未突合なのだから止めるのが正しく、素通しすると仕組みが空洞化する
- hookスクリプト自体が例外で落ちた場合: exit 0 で通す（hookのバグで登録が全面停止する事態を避ける）

## 7. 他スキルとの関係

**`td.py add ... --due` を直接叩いているスキルが7本ある。hookを入れると全部ブロックされるため、登録経路を task-add に通す改修が必須。**

| スキル | 関係 |
|---|---|
| `gyakusan` | イベントから逆算した不足タスクを提案する。承認後の登録は task-add を通す。ただし gyakusan は既に60日分のカレンダーを取得済みのため、そのイベント一覧を渡して `list_events` を再取得させない |
| `ohayo` | 「🧾 タスク登録候補の承認」からの登録が該当。朝の繰越（既存タスクの期限付け替え）はゲート対象外で従来通り |
| `nichijo` | 記録から抽出した「やること」の登録が該当 |
| `iken` / `citizen-inquiry-responder` | 市民相談の次アクション登録が該当。15分級の軽量タスクが多く、判定は即✅になることが多い |
| `smart-intake` | 判定ツリー7番「やること・行動」の登録が該当 |
| `task-audit` | 停滞タスクへの期限**設定**・再連絡タスクの登録が該当 |
| `shisei-houkokukai` | Stage2〜5の推奨日タスク登録が該当 |
| `oyasumi` | 期限据え置きのため関与しない |

hookのdenyメッセージが「task-addを起動せよ」と教えるため、改修を怠っても最終的には自己修復する（deny→task-add起動→登録成功）。ただし毎回1往復を無駄にするので、常道の経路を先に正しくしておく。

## 10. 受け入れ条件

1. `td.py add "テスト" --due 2026-08-10` を突合なしで直接叩くと hook が deny する
2. task-add スキルを通して同じタスクを登録すると成功する
3. 期限なしの `td.py add "テスト"` は hook を素通しする
4. `td.py done <id>` `td.py list` `td.py morning` は素通しする
5. 終日予定のある日は確保可能セッションが 0 として計上される
6. 確保可能セッションが必要セッションを下回るとき、代替期限日が2案提示される
6-2. 「リーフレット入稿」を3日後の期限で登録しようとすると、最低所要日数4日を下回るため空き状況によらず 🚫 になる
6-3. 空きが8時間ある1日があっても、同一タスクにはその日最大2セッションしか計上されない
7. `_verified.json` の TTL 超過後に同じ登録を試みると deny される
8. 既存の Stop hook（sync-to-git.sh）が壊れていない
9. `td.py add` を叩く既存7スキル（gyakusan／ohayo／nichijo／iken／smart-intake／task-audit／shisei-houkokukai）に task-add 経由の但し書きが入っている
10. `~/claude-config/backup/hooks/` に hook 本体がバックアップされ、`_verified.json` はバックアップされていない
