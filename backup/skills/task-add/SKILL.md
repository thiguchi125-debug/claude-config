# task-add — カレンダー突合つきタスク登録

目的: 「実施できない日を期限に設定してしまい、期限切れタスクが積み上がる」を構造的に潰す。**提案止まりが既定**。承認なしにTodoistへ書き込まない。

設計の正本は同ディレクトリの `DESIGN.md`。本ファイルと矛盾したら DESIGN.md が優先。

## Step 1: タスクの整理

登録候補を「内容・登録先プロジェクト案・期限案」の3点に整理する。

- 期限案の既定は**今日+3日**（[[feedback_task_deadline_3days]]・あくまで推奨案であって確定値ではない）
- `python3 ~/.claude/scripts/todoist/td.py projects` で**実在するプロジェクト名を確認**してから `--project` を決める（「📋 政策・一般質問」は実在しない）
- 相手のボール待ち＝`@結果待ち`、やる方向だが要検討＝`@保留`
- **期限を付けない登録**（@アイデア等）はここで終了。Step 2以降は不要で、hookも素通しする

## Step 2: 想定所要の見積り

タスク内容から下表で推定する。**所要は時間の合計ではなく「1時間セッションの回数」で数える。**

| 種別 | 判定語 | 想定所要 | 必要セッション | 最低所要日数 |
|---|---|---|---|---|
| 連絡・電話・アポ取り | 電話／連絡／アポ／確認する | 15分 | 30分枠×1 | 1日 |
| メール・DM返信 | 返信／メール／返事 | 30分 | 30分枠×1 | 1日 |
| 挨拶原稿 | 挨拶／祝辞 | 30分 | 30分枠×1 | 1日 |
| 資料読み込み | 読む／目を通す／資料確認 | 1h | 1h×1 | 1日 |
| ブログ・SNS | ブログ／投稿／発信 | 1h | 1h×1 | 1日 |
| 訪問・現地確認 | 訪問／現地／視察 | 1h | 1h×1 | 1日 |
| 議案分析・調査 | 分析／調査／リサーチ | 3h | 1h×3 | 2日 |
| 一般質問・議案質疑原稿 | 一般質問／質疑／通告 | 4h | 1h×4 | 2日 |
| スライド・報告会資料 | スライド／資料作成／報告会 | 4h | 1h×4 | 2日 |
| 印刷物制作・入稿 | チラシ／ポスター／リーフレット／入稿 | 8h | 1h×8 | 4日 |

- 表に該当が無ければ内容から推定し、根拠を1行添える
- **推定値は提案時に必ず表示する**。草川が「これ30分」と訂正したら再計算する
- 最低所要日数 = `ceil(必要セッション ÷ 2)`（1日に同一タスクへ割けるのは最大2セッションのため）

## Step 3: 早期打ち切り判定

期限候補日までの残り日数が**最低所要日数を下回る**なら、カレンダーを見るまでもなく 🚫 とする。この場合も Step 4 は実施する（代替期限日の算出に空き状況が要るため）。

## Step 4: カレンダー取得

`mcp__claude_ai_Google_Calendar__list_events` を**1回だけ**呼ぶ。

- calendarId = **`kusakawa.taku@gmail.com`**（`kusagawa` は誤り）
- 期間 = 今日 〜 期限候補日+7日（+7日は代替期限案を出すための余白）
- 複数タスクをまとめて登録する場合も、**最も遠い期限候補日+7日までを1回で取る**。タスクごとに呼ばない

gyakusan から呼ばれた場合など、**呼び出し元が既にカレンダーを取得済みならそれを受け取り、再取得しない**。

## Step 5: 空き枠の算出

期限候補日まで（今日を含む）の各日について:

1. 稼働帯 **9:00–21:00**（全曜日・土日祝も同じ）を用意する
2. その日の予定を取得し、重なりをマージする
3. **終日予定が1件でもあれば、その日の確保可能セッションは 0**（議会・出張・終日イベントは作業不可日）
4. 稼働帯から予定を差し引き、残った連続区間を出す。**30分未満の隙間は数えない**
5. その日の確保可能セッション数 = `min(2, 1時間以上の連続区間の合計時間の切り捨て)`
6. 全日の合計を **確保可能セッション数** とする

当日は `max(9:00, 現在時刻)` から算出する。移動時間は考慮しない。

## Step 6: 3値判定

| 判定 | 条件 | 出力 |
|---|---|---|
| ✅ 可能 | 確保可能 ≧ 必要セッション × 1.5 | 着手推奨日を併記 |
| ⚠️ タイト | 必要 ≦ 確保可能 < 必要 × 1.5 | 逼迫の理由（終日予定日等）と着手推奨日を併記 |
| 🚫 無理 | 確保可能 < 必要セッション、または Step 3 で打ち切り | 代替期限日を2案（最短で足りる日／余裕×1.5を満たす日） |

**着手推奨日** = 「その日から期限日までに確保できるセッション数が必要数以上になる」日のうち**最も遅い日**。これ以上先延ばすと間に合わなくなる境界日。

## Step 7: 提案

`python3 ~/.claude/scripts/todoist/td.py week` で**同期間に期限が来る既存タスクの件数**を取り、ヘッダに併記する（所要を推定して空き時間から差し引くことはしない）。

```
📋 タスク登録の確認（カレンダー突合済み 8/3〜8/12・同期間の既存タスク7件）

1. 川合町報告会のスライド作成
   PJ: 🏛 議員活動 ／ 期限案: 8/12(火) ／ 想定: 1h×4回（最低2日）
   確保可能 9回 → ✅ 可能（着手推奨 8/8）

2. ◯◯さんへ回答メール
   PJ: 🏛 議員活動 ／ 期限案: 8/6(木) ／ 想定: 30分枠×1
   確保可能 1回 → ⚠️ タイト（8/5終日議会・8/6は予定4件）

3. リーフレット入稿
   PJ: 🗳 選挙2026 ／ 期限案: 8/8(金) ／ 想定: 1h×8回（最低4日）
   🚫 確保可能 5回 < 必要 8回
      代替案 a) 8/15(金) 確保9回  b) 8/20(水) 確保13回 ●推奨

→ 「1と2」「3はaで」「全部」「見送り」等でお答えください
```

## Step 8: 承認取得

草川の返答を待つ。**返答が無いもの・見送られたものは登録しない。** 既定値で勝手に確定登録しない（[[feedback_ask_destination_and_deadline_before_register]]）。

## Step 9: 突合記録の書込

承認された分だけを `~/.claude/skills/task-add/_verified.json` に書く。この記録が無いと次のStep 10が hook に deny される。

```python
python3 -c "
import json, os
from datetime import datetime
p = os.path.expanduser('~/.claude/skills/task-add/_verified.json')
json.dump({
  'generated_at': datetime.now().isoformat(timespec='seconds'),
  'ttl_minutes': 30,
  'calendar_ok': True,
  'approved': [
    {'content': '<td.py add に渡すのと同じ文字列>', 'due': 'YYYY-MM-DD',
     'sessions': <必要セッション数>, 'verdict': 'ok'},
  ],
}, open(p, 'w'), ensure_ascii=False)
"
```

- `content` は `td.py add` に渡す文字列と**同じもの**を書く（hookは絵文字・空白・記号を無視して照合するので多少の揺れは吸収されるが、揃えておく）
- `due` は `--due` に渡す `YYYY-MM-DD` と**完全一致**させる
- `verdict` は `ok` / `tight` / `unverified`
- TTLは30分。承認から時間が空いたら書き直す

## Step 10: 登録

承認分のみ `td.py add` を実行する。

```bash
python3 ~/.claude/scripts/todoist/td.py add "<内容>" --due YYYY-MM-DD --project "<実在PJ名>" [--priority 1-4] [--label 結果待ち] [--desc "<判定根拠1行>"]
```

`--desc` に「想定1h×4回・確保9回・着手推奨8/8」のような判定根拠を1行入れておくと、後で見返したときに期限の由来が分かる。

登録後、`_verified.json` は放置してよい（30分で失効する）。

## カレンダーが取れないとき

Google Calendar MCP が応答しない場合は突合を諦めて止まるのではなく、次のように進める。

1. 提案に **「⚠️ カレンダー未確認」** と明示する（判定は出さない）
2. 草川の承認を得る
3. `_verified.json` を `calendar_ok: false`・各エントリの `verdict: 'unverified'` で書く
4. 登録する

hook は `calendar_ok` の値で分岐しないので、記録さえあれば通る。**黙って未確認のまま登録しない**ことが要件。

## 📌 恒久ガードルール

- **提案止まりが既定。承認なしのTodoist書込は禁止**（[[feedback_ask_destination_and_deadline_before_register]]）
- 期限案の「今日+3日」は**推奨案であって確定値ではない**（[[feedback_task_deadline_3days]] は上記に上書きされている）
- **想定所要は必ず提示する。** 黙って見積もって黙って判定しない。訂正されたら再計算する
- カレンダーIDは `kusakawa.taku@gmail.com`（`kusagawa` は誤り・CLAUDE.md正本）
- `td.py projects` で**実在PJ名を確認してから** `--project` を指定する
- 1日に同一タスクへ割けるのは**最大2セッション**。空きが8時間ある日でも1タスクには2セッションしか計上しない
- 既存タスクは**件数のみ**併記。所要を推定して空き時間から差し引かない（裏付けのない数字で判定を歪めない）
- `list_events` は**1回だけ**。タスクごとに呼ばない
- まず「記録で足りるか、タスク化が要るか」を振り分ける。方針・状況は記録に残すだけでタスクにしない
- 単発で完結しないタスクは CLAUDE.md「タスク登録時のプロジェクト化判定」基準A〜Eでプロジェクト化要否を問いかける
