# task-add — カレンダー突合つきタスク登録

目的: 「実施できない日を期限に設定してしまい、期限切れタスクが積み上がる」を構造的に潰す。**提案止まりが既定**。承認なしにTodoistへ書き込まない。

設計の正本は同ディレクトリの `DESIGN.md`。本ファイルと矛盾したら DESIGN.md が優先。

## Step 1: タスクの整理

登録候補を「内容・登録先プロジェクト案・期限案」の3点に整理する。

- 期限案の既定は**今日+3日**（[[feedback_task_deadline_3days]]・あくまで推奨案であって確定値ではない）
- `python3 ~/.claude/scripts/todoist/td.py projects` で**実在するプロジェクト名を確認**してから `--project` を決める（「📋 政策・一般質問」は実在しない）
- 相手のボール待ち＝`@結果待ち`、やる方向だが要検討＝`@保留`
- **期限を付けない登録**（@アイデア等）はここで終了。Step 2以降は不要で、hookも素通しする

## Step 2: 想定所要の見積り

タスク内容から下表で推定する。**所要は時間の合計ではなく「30分コマ」の数で数える**（1セッション=1時間=2コマ）。30分粒度にしているのは、電話1本のような30分タスクを1時間単位で切り捨てると「30分空いている日」が0と数えられ、実施可能なのに🚫になるため。

| 種別 | 判定語 | 想定所要 | 必要コマ | 最低所要日数 |
|---|---|---|---|---|
| 連絡・電話・アポ取り | 電話／連絡／アポ／確認する | 15分 | 1コマ | 1日 |
| メール・DM返信 | 返信／メール／返事 | 30分 | 1コマ | 1日 |
| 挨拶原稿 | 挨拶／祝辞 | 30分 | 1コマ | 1日 |
| 資料読み込み | 読む／目を通す／資料確認 | 1h | 2コマ | 1日 |
| ブログ・SNS | ブログ／投稿／発信 | 1h | 2コマ | 1日 |
| 訪問・現地確認 | 訪問／現地／視察 | 1h | 2コマ | 1日 |
| 議案分析・調査 | 分析／調査／リサーチ | 3h | 6コマ | 2日 |
| 一般質問・議案質疑原稿 | 一般質問／質疑／通告 | 4h | 8コマ | 2日 |
| スライド・報告会資料 | スライド／資料作成／報告会 | 4h | 8コマ | 2日 |
| 印刷物制作・入稿 | チラシ／ポスター／リーフレット／入稿 | 8h | 16コマ | 4日 |

- 表に該当が無ければ内容から推定し、根拠を1行添える
- **推定値は提案時に必ず表示する**。草川が「これ30分」と訂正したら再計算する
- 最低所要日数 = `ceil(必要コマ ÷ 4)`（1日に同一タスクへ割けるのは最大2セッション=4コマのため）

## Step 3: カレンダー取得

`mcp__claude_ai_Google_Calendar__list_events` を**1回だけ**呼ぶ。

- calendarId = **`kusakawa.taku@gmail.com`**（`kusagawa` は誤り）
- 期間 = 今日 〜 期限候補日+14日（+14日は代替期限案を出すための余白）
- 複数タスクをまとめて登録する場合も、**最も遠い期限候補日+14日までを1回で取る**。タスクごとに呼ばない
- 草川のカレンダーは予定が密で、2週間分でも応答が7万字を超えて**そのままではコンテキストに載らない**。載らなかった場合はツール結果が自動でファイルに保存されるので、**そのパスをそのまま Step 4 のスクリプトに渡す**（中身を読み下す必要はない）。インラインで返ってきた場合はスクラッチパッドにJSONとして書き出してからパスを渡す

gyakusan から呼ばれた場合など、**呼び出し元が既にカレンダーを取得済みならそれを受け取り、再取得しない**。

## Step 4: 空き枠の算出と判定（スクリプトで行う）

区間のマージ・隙間の足切り・1日上限を手計算すると必ず間違えるので、**同ディレクトリの `sessions.py` を使う**。手で数えない。

```bash
python3 ~/.claude/skills/task-add/sessions.py <events.json> \
  --from <今日 YYYY-MM-DD> --due <期限候補日 YYYY-MM-DD> --need <必要コマ数> \
  [--now HH:MM]
```

出力に日別コマ数・判定・着手推奨日・代替案がそのまま出る。タスクごとに `--due` と `--need` を変えて呼ぶ（カレンダーの取得は1回のまま）。

スクリプトが実装している規則:

1. 稼働帯 **9:00–21:00**（全曜日・土日祝も同じ）。当日は `--now` 以降
2. 予定の重なりはマージする。**30分未満の隙間は使えないものとして捨てる**
3. その日のコマ数 = `min(4, 使える空きの30分単位)`。**1日に同一タスクへ割けるのは最大2セッション=4コマ**
4. **終日予定は原則ブロックしない。** 草川のカレンダーでは終日予定の大半が目印（グラウンドゴルフ・憩いの場・地域行事等）で、実際の拘束は時間指定予定として入っている。一律に作業不可日にするとほぼ全日が0コマになる。「議会／視察／出張／研修／入院／旅行／終日」を含む終日予定だけを**作業不可日（0コマ）**とする
5. **`【参考】` で始まる予定は完全に無視する**（他人の行事等の参考情報であり草川を拘束しない）
6. 移動時間は考慮しない

## Step 5: 3値判定（スクリプト出力の読み方）

| 判定 | 条件 | 提案に書くこと |
|---|---|---|
| ✅ 可能 | 確保可能 ≧ 必要コマ × 1.5 | 着手推奨日を併記 |
| ⚠️ タイト | 必要 ≦ 確保可能 < 必要 × 1.5 | 逼迫の理由（終日拘束日・予定過密日）と着手推奨日を併記 |
| 🚫 無理 | 確保可能 < 必要コマ、**または残り日数 < 最低所要日数** | 代替期限日を2案（最短で足りる日／余裕×1.5を満たす日） |

残り日数が最低所要日数を下回る場合は、空き状況を見るまでもなく 🚫 になる（例: 入稿16コマ＝最低4日を3日後の期限で登録しようとした場合）。

**着手推奨日** = 「その日から期限日までに確保できるコマ数が必要数以上になる」日のうち**最も遅い日**。これ以上先延ばすと間に合わなくなる境界日。

## Step 6: 提案

`python3 ~/.claude/scripts/todoist/td.py week` で**同期間に期限が来る既存タスクの件数**を取り、ヘッダに併記する（所要を推定して空き時間から差し引くことはしない）。

```
📋 タスク登録の確認（カレンダー突合済み 8/3〜8/12・同期間の既存タスク7件）

1. 川合町報告会のスライド作成
   PJ: 🏛 議員活動 ／ 期限案: 8/12(火) ／ 想定: 4h（8コマ・最低2日）
   確保可能 19コマ → ✅ 可能（着手推奨 8/10）

2. ◯◯さんへ回答メール
   PJ: 🏛 議員活動 ／ 期限案: 8/6(木) ／ 想定: 30分（1コマ）
   確保可能 1コマ → ⚠️ タイト（8/4は視察で終日・8/5も予定過密）

3. リーフレット入稿
   PJ: 🗳 選挙2026 ／ 期限案: 8/5(水) ／ 想定: 8h（16コマ・最低4日）
   🚫 残り3日 < 最低4日（確保9コマ < 必要16コマ）
      代替案 a) 8/8(土) 累計19コマ  b) 8/10(月) 累計27コマ ●推奨

→ 「1と2」「3はaで」「全部」「見送り」等でお答えください
```

## Step 7: 承認取得

草川の返答を待つ。**返答が無いもの・見送られたものは登録しない。** 既定値で勝手に確定登録しない（[[feedback_ask_destination_and_deadline_before_register]]）。

## Step 8: 突合記録の書込

承認された分だけを `~/.claude/skills/task-add/_verified.json` に書く。この記録が無いと次のStep 9が hook に deny される。

```python
python3 -c "
import json, os
from datetime import datetime
p = os.path.expanduser('~/.claude/skills/task-add/_verified.json')
json.dump({
  'generated_at': datetime.now().isoformat(timespec='seconds'),
  'ttl_minutes': 30,
  'calendar_ok': True,
  'approved': [
    {'content': '<td.py add に渡すのと同じ文字列>', 'due': 'YYYY-MM-DD',
     'slots': <必要コマ数>, 'verdict': 'ok'},
  ],
}, open(p, 'w'), ensure_ascii=False)
"
```

- `content` は `td.py add` に渡す文字列と**同じもの**を書く（hookは絵文字・空白・記号を無視して照合するので多少の揺れは吸収されるが、揃えておく）
- `due` は `--due` に渡す `YYYY-MM-DD` と**完全一致**させる
- `verdict` は `ok` / `tight` / `unverified`
- TTLは30分。承認から時間が空いたら書き直す

## Step 9: 登録

承認分のみ `td.py add` を実行する。

```bash
python3 ~/.claude/scripts/todoist/td.py add "<内容>" --due YYYY-MM-DD --project "<実在PJ名>" [--priority 1-4] [--label 結果待ち] [--desc "<判定根拠1行>"]
```

`--desc` に「想定4h(8コマ)・確保19コマ・着手推奨8/10」のような判定根拠を1行入れておくと、後で見返したときに期限の由来が分かる。

登録後、`_verified.json` は放置してよい（30分で失効する）。

## カレンダーが取れないとき

Google Calendar MCP が応答しない場合は突合を諦めて止まるのではなく、次のように進める。

1. 提案に **「⚠️ カレンダー未確認」** と明示する（判定は出さない）
2. 草川の承認を得る
3. `_verified.json` を `calendar_ok: false`・各エントリの `verdict: 'unverified'` で書く
4. 登録する

hook は `calendar_ok` の値で分岐しないので、記録さえあれば通る。**黙って未確認のまま登録しない**ことが要件。

## 📌 恒久ガードルール

- **提案止まりが既定。承認なしのTodoist書込は禁止**（[[feedback_ask_destination_and_deadline_before_register]]）
- 期限案の「今日+3日」は**推奨案であって確定値ではない**（[[feedback_task_deadline_3days]] は上記に上書きされている）
- **想定所要は必ず提示する。** 黙って見積もって黙って判定しない。訂正されたら再計算する
- カレンダーIDは `kusakawa.taku@gmail.com`（`kusagawa` は誤り・CLAUDE.md正本）
- `td.py projects` で**実在PJ名を確認してから** `--project` を指定する
- 1日に同一タスクへ割けるのは**最大2セッション（4コマ）**。空きが8時間ある日でも1タスクには4コマしか計上しない
- **空き枠の算出は必ず `sessions.py` に任せる。**区間のマージ・30分未満の足切り・1日上限を手計算すると間違える
- **終日予定を一律に作業不可日としない。**草川のカレンダーでは終日予定の大半が目印であり、一律ブロックするとほぼ全日が0コマになる（2026-08-03 実データで確認）
- 既存タスクは**件数のみ**併記。所要を推定して空き時間から差し引かない（裏付けのない数字で判定を歪めない）
- `list_events` は**1回だけ**。タスクごとに呼ばない
- まず「記録で足りるか、タスク化が要るか」を振り分ける。方針・状況は記録に残すだけでタスクにしない
- 単発で完結しないタスクは CLAUDE.md「タスク登録時のプロジェクト化判定」基準A〜Eでプロジェクト化要否を問いかける
