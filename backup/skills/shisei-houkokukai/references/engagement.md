# 市政報告会 演出ドクトリン（engagement.md）

> 対象読者: SKILL.md（shisei-houkokukai）の Stage1 演出配置案・Stage3 スライド制作・Stage4 台本生成を担当する自分（Claude）。
> 本書は設計書 `/Users/kusakawatakuya/.claude/skills/shisei-houkokukai/design/2026-07-04-shisei-houkokukai-design.md` §5（Stage3 スライド）・§5.5（内容品質体制）の演出ドクトリンを実行可能な指示として成文化したもの。単調な市政報告会を「聞いてよかった・面白かった」に変え、行動の変化につなげるための3軸（参加型／自分ごと化／未来提示）＋禁止事項＋更新規律をここに置く。
>
> 使うタイミング:
> - **Stage1**: 企画シートの「演出配置案」（どの柱の頭にクイズを置くか／どこで自分ごと化するか／締めの分岐とCTAを何にするか）を決めるときに本書の基準を当てる
> - **Stage3**: スライドHTMLを実装するときに本書のパターン・密度基準に沿わせる
> - **Stage4**: ノート・山場フル台本を書くときに本書のキュー記法・CTAメニューを使う

## 1. 参加型（クイズ・問いかけ）

聴衆を受け手から参加者に変える。柱の頭（掴み）に置くのを基本形とする。

### クイズスライド型（2枚ペア構造）

構造は必ず「問題スライド（大きな問い＋選択肢）→次スライドで答え＋なぜそうなのか」の2枚1組。1枚に問いと答えを同居させない（間を作って参加させるのが目的のため）。

HTMLパターン例（テンプレ血統デッキのCSS変数 `--lime:#c7ff4a` / `--green-deep:#0f3d27` / `--green:#1f5a3a` / `--cream:#f3efe4` を前提とした構造スケッチ。実スタイルはテンプレ血統デッキ本体のCSSに従う。data-idはStage3承認後に凍結する識別子で、Stage4のノート・台本はこのIDに1:1で紐付く）:

```html
<!-- 問題スライド -->
<section class="slide slide-quiz-question" data-id="s-<地区>-quiz-<連番>">
  <div class="quiz-badge">CHECK</div>
  <h2 class="quiz-prompt">〇〇、亀山市ではいくらだと思いますか？</h2>
  <ul class="quiz-choices">
    <li>A. 〇〇</li>
    <li>B. 〇〇</li>
    <li>C. 〇〇</li>
  </ul>
  <!-- スピーカーノート（Stage4）: 挙手キューをここに書く -->
</section>

<!-- 答えスライド（直後の1枚） -->
<section class="slide slide-quiz-answer" data-id="s-<地区>-quiz-<連番>-a">
  <div class="answer-badge">ANSWER</div>
  <p class="answer-value">正解は <strong>B</strong></p>
  <p class="answer-why">なぜなら〇〇だからです（一次情報の出典を併記）</p>
</section>
```

- 選択肢は3〜4択を基本とする（多すぎると挙手が割れて間延びする）
- 答えスライドには必ず「なぜそうなのか」を添える。数字だけで終わらせない
- クイズの答え・使う数字は**Stage1企画シート作成時にcontent-fact-checkerで裏取り済み**であることが前提（Stage3では鮮度もののみ再照合）。裏取りされていない数字をクイズに使わない

### 挙手アンケート型（ノート側キュー記法）

スライド本体には設問だけを大きく置き、進行キューはスピーカーノート側に**キュー記法**で持つ。Stage4のノートはこの記法を使う。

```
【挙手キュー】
問い: 「〇〇したことがある方、手を挙げてください」
間: 3秒待つ（早く答えを言わない）
拾い方: 挙がった手のおおよその割合を口頭で言い添える（「半分くらいですね」等）
外れ／反応薄いときの受け: 「意外と少ないですね、実は〇〇なんです」で本題に接続する
```

- キューは「問い」「間」「拾い方」「反応薄いときの受け」の4項目を最低限そろえる。間を明記しないと台本が棒読みになる

### 密度基準

- **出発点**: 30分枠で参加ポイント2回以上、60分枠で3〜4回
- **この基準の機械適用禁止**。Stage1の地区解像度ヒアリングで得た「当日の顔ぶれ」（年齢層・人数感・関心度）に応じて増減する。例: 少人数・高齢層中心の顔ぶれなら挙手型の頻度を下げ、対話型（「〇〇さん、どう思われますか」的な呼びかけ）に寄せる。逆に子育て世代中心・人数が多い会場ではクイズ回数を増やしてよい
- 各柱の頭に参加ポイントを置くのを基本形とする（柱の掴み＝参加、という配置がデフォルト）。ただし顔ぶれ次第でこの配置も調整可

## 2. 自分ごと化（地元密着）

一般論の報告会で終わらせず、「これは自分たちの話だ」と感じさせる。

- **各柱に地区固有スライドを最低1枚**入れる。固有性の源は道路名・学校名・自治会名・地図・Before/After写真のいずれか（一般的な制度説明だけの柱を作らない）
- 見出しは可能な限り「皆さんの〜」「この地区の〜」を主語にする。「亀山市では」ではなく「皆さんの〇〇地区では」「この地区の〇〇では」という書き方をデフォルトにする
- **一般論スライド（制度説明・全市データ等）の直後には必ず「では〇〇地区では？」の接続スライドまたは接続フレーズを入れる**。全市の話をして終わりにせず、必ずこの地区に折り返す。接続先は地区固有スライド（上記）であることが多い
- 地区固有スライドの素材（固有名詞・地図・写真）はStage1企画シートの「地区カルテ」（district-issue-scoutの出力＋地区解像度ヒアリング結果）から拾う。Stage3で新規に地区情報を調べ直さない

## 3. 未来提示（選択肢を渡す）

報告会を「聞いて終わり」にせず、聴衆が選び取れる形で先を見せる。

### 分岐スライド（締めブロック）

締めブロックに必ず1枚、「このままだと…／こうすれば…」の2列対比スライドを置く。

```html
<section class="slide slide-branch" data-id="s-<地区>-branch">
  <h2>この地区の、これから</h2>
  <div class="branch-columns">
    <div class="branch-col branch-asis">
      <h3>このままだと</h3>
      <p>〇〇（現状の延長線上のリスク・課題。裏取り済みの事実ベース）</p>
    </div>
    <div class="branch-col branch-tobe">
      <h3>こうすれば</h3>
      <p>〇〇（具体的な選択・行動によって変わる先。誇張しない）</p>
    </div>
  </div>
</section>
```

- 「このままだと」列は不安を煽る誇張表現にしない。裏取りされた事実の延長線として書く（架空エピソード禁止・抽象詩的比喩禁止と同じ規律）
- 「こうすれば」列は聴衆が実際に取れる行動・市が進めている選択肢に接続する。実現性のない空約束を書かない

### 最終CTA = 行動メニュー型（4種を基本セットとする）

最後のスライドは単一の「ご清聴ありがとうございました」で終わらせず、聴衆が次に取れる行動を複数メニューで提示する。基本の4種:

1. **声を寄せる**（ご意見箱・公式LINE）
2. **AIインタビュー参加**（`https://depth-interview-kusagawa.vercel.app/`）
3. **アンケート回答**
4. **次回参加**（次の報告会・自治会行事等への案内）

- 4種すべてを毎回フルで並べる必要はないが、**単一CTA（「ご意見をお寄せください」のみ等）で終わらせない**。最低2種以上を提示する
- AIインタビューのURLは正確に転記する（typo・省略禁止）。参加呼びかけの定型注意事項（個人情報の扱い等）は既存ルール（[[feedback_ai_interview_participation_call_required]] 相当の運用）に従う

## 4. 禁止・注意（ハードルール）

以下はスライド・台本のいずれにも例外なく適用する。Stage3のcontent-risk-reviewer・Stage4の安全2ゲートで最終確認するが、生成段階から自己遵守する。

- **架空エピソード禁止**: 感情演出のための作り話・実体験を装った創作をしない。実体験・一次情報・公式データのみを使う
- **他議員氏名禁止**: 対外発信物（スライド・配布物・台本）に他の議員の実名を一切載せない。議事録から拾った事実は「他議員が引き出した数字」等の汎用表記に変換する
- **議事録引用は草川発言＋市答弁ペアのみ**: 議事録・会議録から引用する際は、草川たくやの発言と亀山市側答弁（市長・副市長・教育長・各部長等）のペアだけを切り出す。他議員の質疑ブロックはスライド・台本に使わない
- **抽象・詩的比喩禁止**: 「未来への架け橋」のような情緒的メタファーで内容を薄めない。数字・固有名詞・具体的な行動で書く
- **絵文字なし**: スライド・解説カードのいずれにも絵文字を装飾として使わない（見出しの区切り記号やCSS上のマーカー表現は可。絵文字そのものを禁止）
- **クイズの答えは一次情報裏取り必須**: クイズで使う数字・事実は必ずcontent-fact-checkerによる一次情報照合を経たものだけを使う。Stage1企画シート段階で裏取り済みが前提であり、Stage3では新規追加分と鮮度もの（直近議会の議決状況等）のみ再照合する

## 5. 実開催からの更新（腐敗防止）

本ドクトリンは一度書いて終わりにしない。実際の開催結果と乖離したまま放置すると、システムの法則どおり「記憶依存の締め」が腐る（[[feedback_system_closing_loops_rot]]）。

- 本ドクトリンは、実開催後に🎤市政報告会DBへ残される「演出の効きメモ」（クイズは答えが出たか・どこで空気が緩んだか・参加者数／質問件数）と定期的に照合する
- 効きメモの内容が本書の基準（密度基準・配置基準・CTA構成等）と乖離してきたら本書を更新する
- 更新提案の入口はStage5前夜チェック後の声記録リマインド（設計書§7-4）を経由する。Stage5が「演出の効きメモを残すように」促し、次回Stage1でその蓄積を読んだ結果、基準とのズレが見えたタイミングで更新を提案する
- 更新したときは、本節末尾に改訂履歴を1行追記する（日付・変更点・根拠となった開催回を明記）
