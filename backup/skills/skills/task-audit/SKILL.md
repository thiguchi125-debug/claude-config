# 🧹 task-audit — タスク監査・定期棚卸しスキル

## 🔴 Todoist一本化（2026-06-14〜・最優先）
タスク管理は Notion✅タスクDB→**Todoistへ移行済み**。本スキルの棚卸し対象も **Todoist**（`python3 ~/.claude/scripts/todoist/td.py audit` ／ `overdue` ／ `nodue`）。Notion✅タスクDB(`292cf503`)は新規登録に使わず参照のみ。PJ化判定は🗂プロジェクト・プラットフォーム(ds=`8975c6a9`)のPJページ＋Todoist地区/イベント箱で行う。旧Notion前提の6チェックはTodoistの期限なし/期限超過/＠結果待ち/＠保留に読み替える。

## 設計思想

**ohayoに「シグナル」を組み込み、本格処理はこのスキルで手動起動**。理由：
- ohayoが燃費圧迫しない（朝のブリーフィングは70-90K目標を堅持）
- 草川が認知負荷の都合に合わせて頻度自己制御できる
- cron不要・自動化しすぎない

## モード設計（3パターン）

### ⚡ quick（既定・即実行）
- 期限なしinbox全件のみ棚卸し
- 推奨スタンス提示→バッチ承認1回で一括処理
- 所要：5-10分、燃費：40-60K

### 🔍 standard（軽量本格）
- 期限なしinbox + 停滞inbox（4日以上）+ 長期Waiting（60日以上）
- 各カテゴリで推奨スタンス提示→カテゴリ別バッチ承認
- 所要：15-20分、燃費：80-120K

### 🧹 full（月次大棚卸し）
- standard + 停滞PJ次の一手タスク提案 + PJ化候補抽出
- PJ化候補は基準A-Eを自動付与してプロジェクトDB格上げまで一気通貫
- 所要：30-45分、燃費：150-250K

## 6つの自動チェック

### 1. 🟢 期限なし inbox
- 専用view（`📋 期限なしinbox（棚卸し用）` view://35dcf503-a68f-8130-90fa-000ce264c871）を叩く
- ステータス=inbox かつ 期限が空のタスクを抽出
- 推奨スタンス：
  - 要約が明確・アクション具体 → 期限「今日+3日」設定（メモリ`feedback_task_deadline_3days.md`準拠）
  - 要約空・タイトルのみ → Archive推奨
  - 複数タスク連動・継続性高 → PJ格上げ推奨

### 2. 🟡 停滞 inbox
- view「すべて」を叩き、ローカルで `ステータス=inbox かつ 期限 < 今日-4日 かつ 更新日 < 今日-4日` でフィルタ
- 4日以上動いていない期限超過タスクを抽出
- 推奨スタンス：
  - 期限再設定（今日+3日）
  - Done判定確認（実は完了済の可能性）
  - Wish List 退避（連絡まち化）

### 3. 🟠 長期 Waiting
- view「すべて」を叩き、ローカルで `ステータス=Waiting かつ 更新日 < 今日-60日` でフィルタ
- 60日以上動いていないWaitingタスクを抽出（連絡まち忘却防止）
- 推奨スタンス：
  - 強制再連絡（連絡まちは生きてるか確認）
  - Archive（連絡途絶 or 自然解消）
  - inbox復帰

### 4. 🔵 停滞 PJ
- プロジェクトDB全件取得（`collection://292cf503-a68f-81fe-bd40-000b64314f2e`）
- ステータス=「進行中」or「計画中」or「バックログ」かつ 関連タスク0件 or 全Done/Archive のPJを抽出
- 推奨スタンス：
  - 次の一手タスク自動提案（PJ要約から「初動」タスク1件をドラフト）
  - PJステータス変更（中止 or 完了）
  - 関連タスクの紐付け追加（既存タスクからPJに紐付け）

### 5. 🟣 PJ化候補
- inboxタスク全件をローカルクラスタリング：
  - 同一テーマキーワード3件以上（例：「がん検診」「菅内交差点」「障害福祉」など）
  - 同一相談者・同一プロジェクト軸 etc
- 基準A-E自動付与：
  - A: 同一テーマで関連タスク2件以上
  - B: 同テーマ散在3件以上
  - C: 着手〜完了が2週間超
  - D: 複数ステークホルダー絡み
  - E: 「〜検討」「〜整備」「〜推進」等の継続性ある語感
- 推奨スタンス：プロジェクトDB格上げ（PJ名・由来・期間自動設定）

### 6. ⚫ 死蔵ステータス
- タスクDB schema をfetchして status options を確認
- 使用件数ゼロのステータス（例：Remind/Project/Waiting）を検出
- 推奨スタンス：UI手動削除を案内（APIで削除不可のため）

## 実行ワークフロー

### Step 1: モード判定
草川指示から quick / standard / full を判定。曖昧な場合は AskUserQuestion で確認。

### Step 2: データ取得
モードに応じて必要なviewを叩く。並列実行で時短：
- quick: 期限なしinbox view 1本
- standard: 期限なしinbox + 「すべて」 + Waiting抽出
- full: standard + プロジェクトDB + 全inbox（PJ化候補クラスタリング用）

### Step 3: 推奨スタンス計算（ローカル処理）
取得データをローカルでフィルタ・クラスタリング・スタンス判定。Notion API呼出しなしの処理。

### Step 4: バッチ承認 UI
各カテゴリで AskUserQuestion を1回ずつ：

```
🟢 期限なしinbox 12件 — どう処理しますか？

A. 全推奨どおり実行（期限設定8件・Archive3件・PJ格上げ1件）
B. Archive のみ実行、期限設定・PJ格上げは個別判断
C. 1件ずつ確認
D. 今回はスキップ
```

### Step 5: 一括実行
草川承認後、並列で notion-update-page / notion-create-pages を実行。

### Step 6: 結果サマリ
処理件数を集計してチャット出力＋メモリログ追記。Notionの「📔 タスク監査ログ」ページに月次蓄積。

## 禁止事項

- **草川判断なしのArchive一括実行は禁止**：データロス防止のため、必ずバッチ承認を取る
- **stop-iter禁止**：途中で「もう疲れたから残りスキップ」をしない。全カテゴリ完了まで走る or 草川指示で明示的に中断
- **ohayoの中で重い処理を実行しない**：ohayoはシグナル表示のみ、本格処理はこのスキル
- **cron化禁止**：自動化しすぎると草川の認知制御が利かなくなる。あくまで手動起動

## トークン消費目安

- quick: 40-60K
- standard: 80-120K
- full: 150-250K

月平均運用見込み：
- quick × 月2回 + standard × 月1回 + full × 四半期1回 = **約 250-400K/月**
- 棚卸しをしないと「期限なし放置」「停滞PJ」が累積し、半年後に1,000K超の集中棚卸しが発生するため、定期実行が経済合理的。
