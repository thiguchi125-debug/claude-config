### 取得時の必須策
1. **DBビューは「本日アクティブ」filtered view を最優先**で使う。filtered view が DBに存在しない場合は、草川に「軽量view（タスク=期限<=今日かつステータス∉Done/Archive、ニュース=本日付、プロジェクト=ステータス=進行中）を作るか」を提案し、承認時に notion-create-view で作成（1度だけ）。本セッション中はfallbackで全件取得 → ローカルフィルタを実施するが、概算消費トークンを末尾で草川に報告する。

2. **ダッシュボードのfetchは1回限り**。Step 4 の old_str 抽出と verify の両方で同じテキストを使い回す（再fetch禁止）。verify自体も「短い見出し置換のみで構成された場合」は省略可。

3. **本文置換よりチャット出力優先（2026-05-06草川合意）**。Notion ダッシュボード更新は「見出しの日付置換」のみとし、本文（スケジュール詳細・フォーカス本文・ニュース本文・選挙進捗本文・タスクテーブル）の置換は**省略**する。最新情報はチャット出力に集約し、草川がチャットで読めば足りる。「ダッシュボードに最新タスクテーブルを反映」は燃費がかかりすぎるため非必須化。

4. **進行中プロジェクトは件数フィルタのみ**：DB全件取得後、ローカルで`ステータス=進行中` のみ通すが、その時点でtask配列を展開しない。次アクションはタスクDB側の最新クエリ結果から逆引き。

5. **ニュースDBは6件まで**。本日付フィルタ後の亀山関連度上位6件を採用し、残りは「他N件はDBで」で打ち切り。一行コメントは50字以内。

6. **同一セッション内のoyasumi/直前ohayoの取得結果を再利用**：Calendar・Gmailは24h以内のキャッシュがあれば省略。

7. **notion-query-database-view は page_size 引数を持たない**ため、view全件返却を絞る唯一の手段は「view側でfilter済みのものを叩く」。filter付きview作成こそが最効率化策。

- 「📌 運用クイックリンク」「📌 クイックリンク」セクションは絶対に編集しない（草川手動管理）。重複検出時はチャットで警告のみ。
- ダッシュボード末尾の「📚 情報ハブ一覧」「ナビゲーションマップ」は編集しない。

#### 3-0. 📰 ニュースDB — 今朝のニュース

**取得方法（必ずこの順序で実施・分岐を勝手に変えないこと）**：

##### Step A（必須・最初に試す）: 「本日のニュース」filtered view を叩く（2026-05-06軽量化版）

**前準備**: ohayo起動時、まず `notion-update-view` でこのviewの filter 日付を本日に書き換える。固定日付指定（DSLが relative date を非サポートのため）。

```
update_view view_url: https://www.notion.so/f2eefc669dd54648bbcdacdc8afa1158?v=357cf503a68f81e0b678000ca149e75e
configure: CLEAR FILTER; FILTER "日付" = "<today YYYY-MM-DD>"; SORT BY "亀山関連度" DESC
```

その後、本viewを叩く：

```
view_url: https://www.notion.so/f2eefc669dd54648bbcdacdc8afa1158?v=357cf503a68f81e0b678000ca149e75e
```

→ 本日付のニュースのみ6〜10件返却（亀山関連度降順ソート済）。ローカルfilter不要。**70件→6件で約10分の1にトークン削減**。

**fallback**: 上記更新／取得が失敗した場合のみ、旧Default view (`?v=9d34f9a4-2bc1-4381-a31b-8f8c8ac719e2`) で全件取得→ローカルフィルタ。

##### Step B（Step A で日付プロパティを絞り込めなかった場合のみ）: notion-search でDB内検索

```
data_source_url: collection://29e5c1a2-d64d-4822-81fd-0d642c3f07bc
filters: { "created_date_range": { "start_date": "YYYY-MM-DD", "end_date": "YYYY-MM-DD+1" } }
query: "."   ← セマンティック検索を空回りさせる空クエリ。`"ニュース"` 等の単語は禁止（見出しに含まれないため0件になる）
```

##### ⚠️ よくある失敗パターン（過去事故 2026-04-29 踏まえ）

**事故事例（2026-04-29）**：
- `notion-search query="ニュース"` を叩いたが、ニュース見出しに「ニュース」の語がなく**0件返却**
- `data_source_url: collection://f2eefc66-fa30-...` は**database top-level ID**であり data source IDではないため `validation_error: Invalid Data Source URL`
- 結果、cronで本日分8件が正常に収集されていたにも関わらず「未収集」と誤判定

**対策**：
- Step A の view_url は固定値。**変更しないこと**
- collection ID を間違えない: ✅`29e5c1a2-d64d-4822-81fd-0d642c3f07bc`（data source）／❌`f2eefc66-fa30-4f57-...`（database top-level、data_source_url には使えない）
- query パラメータには `"."` または空文字に近いものを使う。**意味のある単語は禁止**

##### 取得後の処理

- `日付` プロパティで本日（YYYY-MM-DD）のものをローカルフィルタ
- ソート: `亀山関連度` 降順、同順なら `カテゴリ` 順

- **iJAMP由来（概要冒頭に `【iJAMP配信／🔒内部閲覧専用】` を持つ記事）はこのセクションから除外し、§3-0b 他自治体好事例セクションに移送**

#### 3-1b. 今日のタスク（タスクDBから直接取得 — 必ず実DBクエリ）

**⚠️ 重要（2026-04-30事故踏まえ）**: ダッシュボードのタスクテーブルを再利用してはならない。Done/Archive済みのタスクが残っていたり、本日の新規タスクを取りこぼしたりする。**毎朝必ず実DBに最新クエリを投げる**。

#### old_str の取り方（重要・2026-05-01 燃費精査で改訂）

**old_str は必ず以下の形式で組む：**

##### 🟢 推奨パターン：「見出し1行のみ置換」+「直下ブロックを別 old_str で置換」

**理由**：
- 見出し行は短く特殊文字が少ない → マッチ成功率ほぼ100%
- 長い本文を1回で置換しようとすると `🌷` `〜` `（）` `*強調*` `《》` 等の細かい記号差で**サイレント失敗**（Notion保存時の正規化／コピペ時のescape差）
- 1回目の update でマッチ失敗すると、補修update（2回目・3回目）が積み上がって燃費悪化（2026-05-01 ohayo 実行で update_page 3回連打 → 約10%トークン浪費の事故）

**実装例（セクション1スケジュール置換）**：
```jsonc
[
  {"old_str": "## 📅 今日のスケジュール（2026年4月30日 木曜日）", "new_str": "## 📅 今日のスケジュール（2026年5月1日 金曜日）"},
  {"old_str": "- 終日　🌷 川合町憩いの場（13:30〜）\n- 13:30〜14:30　赤ちゃん食堂話し合い\n- 14:00〜18:00　挨拶まわり\n- 18:00〜18:30　街頭演説", "new_str": "- 06:30〜07:00　街頭活動\n- 08:30〜09:30　スパイラルガーデン現場視察\n- 13:00〜13:30　議会事務局へ\n- ..."}
]
```

**ルール**：
- 見出し変更は**見出し1行のみ** old_str に入れる（次の `##` まで含めない）
- 本文の置換は**3〜5行程度のブロック単位**で別 old_str に切り出す
- 1セクション全体（見出し＋本文＋区切り）を1つの old_str にする運用は**禁止**

##### 🔴 マッチ失敗の罠（過去事故）

`update_content` は `old_str` がマッチしない場合**エラーを返さず黙ってスキップ**する。失敗の典型パターン：

- **長文 old_str（5行超）**：マッチ失敗確率が高い。**3〜5行に分割**
- **特殊文字の取り違え**：unicode escape は禁止、平文で書く
- **HTMLテーブル・番号付きリストの部分置換は番号体系が壊れる**：必ず`<table>` ... `</table>` 全体を一括置換（テーブルは例外的に長くてOK）
- **複数 content_updates を1回で送ると判別不能**：成功・失敗が混在しても返値で判別不可。verify 必須

##### 必須：fetch verify（更新後の検証）

**`update_content` 呼び出し後、原則 `notion-fetch` 再取得は1回のみ**（2026-05-01 燃費精査）。  
**verify を省略してよい条件**：マッチ失敗の可能性が低い「見出し1行置換のみ」「短いブロック置換のみ」だけで構成され、かつ `replace_all_matches` を使っていない場合は、verify を skip 可。

**verify が必要な場合**（以下のいずれか該当）：
- 1回の update_content に5件以上の content_updates を含めた
- old_str が5行超の長文ブロックを含む
- HTMLテーブル全体置換を含む
- `replace_all_matches: true` を使った

verify 実施時は1回 `notion-fetch` で再取得し、以下をassertする：
1. `## 🎯 今日のフォーカス（YYYY-MM-DD）` の日付が今日になっているか
2. `## 📅 今日のスケジュール（YYYY年M月D日 曜日）` の日付が今日になっているか
3. `## 📬 重要メール・要対応（YYYY年M月D日更新）` の日付が今日になっているか
4. タスクテーブルの番号が `<td>1</td>` から連番で重複なく並んでいるか
5. 古い箇条書き（前日のフォーカス内容など）が残っていないか
6. ~~`## ✅ 本日のルーティン` セクションに `- [x] ` が1個も残っていないか~~（**2026-05-08 廃止：本セクションへの書込み停止**）
7. **タスクテーブルの全行が Step 3-1b で取得した最新DBクエリ結果と一致しているか**（Done/Archive を含まない・本日期限inboxを含む・件数が新しい・古いタイトルの残骸ゼロ — 2026-04-30事故踏まえ最重要）

**assert失敗時はチャットに警告を表示してユーザーに知らせる。無音スキップは絶対禁止。** マッチ失敗箇所を特定し、平文の短い `old_str` で再試行する。

## 注意事項

- データ取得は4つのソース（Calendar・Gmail・Notion各種・ニュースDB）同時並行で行い、レスポンスを速くする
- ニュース欄はDB読み出しのみ（軽量）。新規取得が必要な場合はnews-briefingスキルへ委譲し、ohayo内でWebSearchを呼ばない
- メールは件名と送信者のみ表示し、本文は含めない（プライバシー配慮）
- Notionのタスクは完了済みのものは除外する
- 「今日のフォーカス」はデータから機械的に出すのではなく、ユーザーの状況を読んで1〜2文で端的にまとめる
- 全体で画面1スクロール以内に収まるよう簡潔にする（ただし「今日のタスク」テーブルは件数にかかわらず全件表示する — 折り畳みや「他◯件」と省略するのは禁止）
- **Notion書き込み（Step 4）は必ず実行する。「ページが最新そう」「同じ内容になる」などの理由でスキップしてはならない**
- **タスク・SNS下書きの数値は必ずDBクエリの結果そのまま出す**。恣意的に絞り込んだり「代表例として2件」という表現で実数と異なる件数を提示するのは禁止
