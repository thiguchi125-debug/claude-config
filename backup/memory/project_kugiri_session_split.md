トークン消費の真因は「作り直しの回数」ではなく**セッションを区切らないこと**。2026-09-01〜02の実測（`e02e916f`）は24.5時間・227回で100.1M、うち**出力は0.90M（0.9%）**、残り99.1%が会話の再送だった。文脈は82K→988Kまで伸び、文脈500K超で回した40%の呼び出しがコストの67%を占めた。文脈988Kでは `ls` 1回もブログ1版も同じ約1M。

運用は **「区切り」→ `/clear` → 「再開」の3語**だけ。仕組み：
- `context_budget_notice.py`（PostToolUse）— 120K/200K/300K、**300K超は100Kごと**に警告。旧実装は300Kで永久沈黙し、実測セッションは300K→988Kを無警告で走って約50M浪費した。約30K超のツール結果（Notion MCPが常習）も検出する
- `handoff_notice.py`（SessionStart）— `~/.claude/handoff/archive/` の24時間以内のメモ（最大3件）を案件名付きで新セッション冒頭へ自動注入。複数なら再開時に案件を1問で確認。**LAST.md は2026-09-05廃止**：同日08:19〜08:24に3セッションが同時区切りで1枠を上書きし合い、ブログの再開2本が別案件（発信フローA-1棚卸し）を二重実行した（仕分け表が2枚・退避は _trash_pending_2026-09-05/）
- `/kugiri` スキル ＋ `python3 ~/.claude/scripts/ctx_now.py`（文脈の実測）

**Why:** 文脈は減らないので、区切る以外に効く手段が無い。区切りの代償は起動固定費73Kだけで、文脈300K超なら切れば必ず得（100回ごとで▲53%、60回ごとで▲66%）。

**How to apply:** 警告が出たら `/kugiri`。300K未満なら切らない（払い損）。ただし別件を始めるときは文脈が全部死重になるので必ず切る。引き継ぎメモは20行・1500字以内を厳守する（長い引き継ぎは節約を打ち消す）。handoff配下は並行セッションが消し合うので実体は必ず `archive/` に置く（[[feedback-gate-json-concurrent-overwrite]] と同じ構造）。効果測定は `token_report.py 14 09-02`。分析の正本は `drafts/2026-09-02_トークン消費_原因分析と対策.md`。
