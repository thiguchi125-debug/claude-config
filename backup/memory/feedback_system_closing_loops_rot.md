2026-06-13 のシステム全体検証で判明した構造的法則。

**法則：自動で発火する仕組み（cron/launchd/クラウドRoutine）は全部生きている。人間が「忘れずにやる」前提の"締めの工程"は、例外なく腐っている。**

**Why:** トリガーが無い工程には担当者がいない。だから作りっぱなし・入れっぱなしで誰も締めない・しまわない・消さない・切り替えない。草川本人も気づかないまま死蔵が進む。

検証時の実証（鮮度＝出力日で判定）：
- 🟢生きている（自動トリガー有り）：夜間Driveパイプライン(launchd)／ニュースDB(朝6時cron 6/12まで)／nichijo日次ログ(oyasumi routine 6/12まで)／SNS投稿管理DB／Drive↔ローカル同期(OS daemon)
- 🔴腐っている（人の記憶依存）：
  - **ブログ→アーカイブ還流＝断絶**：ブログはNotionで終わり、grep可能なアーカイブ(02_publications/blog)へ戻る導線が無い。2026-05-04の一括取込1回きりで停止＝以降40日分の自作ブログが未来grep圏外。過去発言を毎回grep参照する運用なのに、自分の発言が消えていく。
  - **議会モード＝死亡**（→廃止済[[feedback_system_closing_loops_rot]]本体の隣・MEMORY.md参照）：誰もフラグを読まない死んだスイッチ。
  - **タスク締め＝滞留**：期限超過inboxが30件超(5/20-22期限が3週間放置)。やった/やってないが不明のまま。
  - **drafts/＝ゴミ箱化**：85件溜まり・5/3から未清掃・完成品も還流せず。
  - **memory剪定＝墓場化**：188ファイル・"進行中"PJ129行に放棄案件多数(マイドライブ全件取込 残147件resume後・Notion埋没ページ大掃除 中断中 等)。

**How to apply:**
1. 新しい仕組み・スキルを作るとき、「締めの工程（しまう/締める/消す/切り替える）」を必ず**定時トリガーに載せる**。人の記憶に頼る設計にしない。例＝おやすみに「完了ブログ→アーカイブ還流」「drafts古いもの掃除」、ohayoに必要なら「カレンダー日程から会期自動判定」。
2. 「議会モード」のような**手動スイッチは作らない**。状態はカレンダー/ファイルの月など**機械が読める一次情報から自動導出**する（drive-intakeが会期を月から自動判定しているのが正解パターン）。
3. 定期的に同じ目線で棚卸し＝「スキル/メモリが"こう動く"と言っていることを信じず、出力の鮮度・ログ・滞留で実際に流れているか判定する」。鮮度が数週間古い＝その工程は死んでいる。
4. まだ洗っていない死蔵が残っている可能性大（今日は議会モード＝死亡・ブログ還流＝断絶の2つを確認。03_themes 5/21停滞・市民意見リスト5/29鈍化も要追跡）。
