2026-05-11 AI×亀山市政ブログ1本生成で推定**400-500K**トークンを消費した。フローの構造的問題を抽出し、新パイプラインで**150-200K（50-60%削減）**を目標化。

## 問題点（旧フロー）

1. **並列リサーチ3並列の過剰起動** — 推定120K
   - policy-expert-DX + 亀山現状 + 草川過去発言の3並列が自動デフォルト
   - 過去発言抽出は「自己引用ブロック生成」の温床になり、草川指摘で削除対象に。コスト払って質を下げた

2. **blog-writer規定字数超過を草川判断に投げた** — 二度手間
   - 規定上限2,500字に対し3,279字（30%超）で出力
   - 「圧縮するか草川判断」型に投げた結果、保存後にやり直し
   - blog-writer指示文で字数厳守させるべき

3. **草川目視前にfact-checker/risk-reviewerを起動** — 推定140K
   - 「ゲート通過＝保存OK」フローで草川承認前にNotion保存
   - 構成の気持ち悪さ（自己引用過剰）はゲートでは検出できない
   - 結果v1保存→v2上書きの二度手間（notion-saver 51K + 直接update 2K）

4. **agent指示文でフレーズ強制継承を指示** — 質と量の両方に悪影響
   - blog-writer指示文に「3層フレーム」「人のぬくもり」を"必ず継承"と明記
   - agent が無理に組み込もうとして冗長＋自己引用ブロック化
   - 「voice-dna保持」程度の抽象指示で十分

5. **policy-archive-miner相当の指示で「強いフレーズ」抽出を促した** — 自己引用の原因
   - 「ブログ再利用できる強いフレーズ」を出させた → blog-writerが採用 → 自己引用ブロック化
   - 過去発言抽出が必要でも「参考資料として保持」に留め、フレーズ強制ピックは依頼しない

## 新パイプライン（草川承認版）

### ステップ1: リサーチ（並列2本がデフォルト）
- **事実調査**（kameyama-researcher or domain-expert）
- **先進事例**（policy-comparison-benchmarker or policy-researcher）
- 過去発言抽出（policy-archive-miner）は**オプション**：自分史開示記事・実績まとめ記事に限定
- 推定60-80K（旧120Kから削減）

### ステップ2: blog-writer
- 字数規定厳守（2,500字上限）、超過時は自動圧縮してから出力
- 指示文では voice-dna 保持を抽象指示に留める。具体フレーズ強制継承は禁止
- 過去発言は「文脈で慎重判断」（feedback_blog_self_quote_careful.md 参照）
- 推定40-60K

### ステップ3: 草川目視（v1ドラフト）
- **ゲート起動前に草川がドラフトを目視**
- 構成・トーン・自己引用バランスの判断は人間が行う
- OKならゲートへ、要修正なら指示

### ステップ4: fact-checker + risk-reviewer 並列
- 草川がOK出した版に対してのみ実行
- 推定100K（並列）

### ステップ5: 修正→草川最終承認→Notion保存（1回完結）
- 修正はEdit最小手数、agent再起動は最終手段
- 保存は1回完結（D2原則厳守）
- 推定10-20K

**合計目標: 150-200K**（旧フロー400-500Kから50-60%削減）

## Why
- 朝のohayoと同様に「ブログ生成も燃費KPI管理対象」とすべき
- 草川承認前にNotion保存するのはD2原則違反
- agent指示文でのフレーズ強制継承は質を下げる
- 並列起動は「便利」だが、必要性吟味なき自動デフォルト化は禁物

## How to apply
- 次回ブログ生成依頼時、まず「自分史記事かor提案型記事か」を判定 → リサーチを2並列にする
- blog-writer指示文に必ず「字数厳守・自動圧縮・voice-dna抽象保持・フレーズ強制継承禁止」を明記
- blog-writer出力後、**ゲート起動前に草川目視を必ず挟む**（auto modeでもこのstepは省略禁止）
- 過去発言抽出agentを呼ぶ場合は「強いフレーズ抽出」依頼を外し、「文脈整理のみ」に限定
- 完了時に消費トークン概算を報告（KPI管理のため）
