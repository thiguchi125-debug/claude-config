Notion update_content で見出し置換が「連続失敗」する場合の根本原因と対処（2026-05-10 ohayo セッション実測）。

## 観測された症状

1. update_page (update_content) を1回送信 → timeout エラー
2. 直後に notion-fetch で再取得 → ページは「未更新の状態」（5/9 のスケジュール）に見える
3. 再送信 → "No matches found" エラー（old_str が見つからない）
4. さらに小さい old_str に分解して再送信 → 同じエラー
5. 後で別タイミングで notion-fetch すると、**最初の送信が実は反映されていた**ことが判明

## 根本原因

**notion-fetch がキャッシュ的な古いスナップショットを返すケースがある**。fetch 結果に `as of YYYY-MM-DDTHH:MM:SS.xxxZ` のタイムスタンプがあり、これが「数十分前」を指していることがある。同じセッション内の連続 fetch でも更新されない。

→ これにより：
- 「ページはまだ更新されていない」と誤判定
- 古いスナップショットからコピーした old_str を送るが、サーバ側は既に新しい状態 → マッチしない

## 対処（必須運用）

### A. timeout 後の判定ルール
`update_page` が timeout を返したら、以下の手順を踏む：
1. **30秒以上待つ**（サーバ側の確定処理を待つ）
2. 別の操作（軽い検索 etc）を1つ挟む
3. 再 fetch して確認
4. それでも反映が見えないなら、**古いキャッシュの可能性あり**として再送信は控える
5. 草川にチャットで「timeout 発生・反映状態は次回 ohayo で確認」と1行報告

### B. content_updates 配列の "No matches" エラー解釈
エラーメッセージが**全old_str を改行連結した文字列**を含む場合：
- API が複数 old_str を**OR ではなく AND（全一致）として扱おうとしている**バグ的挙動
- 1件ずつ単発の content_updates で送り直す（バッチ送信を諦める）

### C. 見出し置換の old_str 規則（2026-05-10 修正版）
- ✅ "## 📅 今日のスケジュール（2026年5月9日 土曜日）" のような完全マッチを使う
- ❌ 部分マッチ（"今日のスケジュール" だけ）は逆にマッチしないケースが多い
- ❌ 「次の見出しまで」を含めない（区切り `---` まで取り込もうとして失敗）

### D. ohayo SKILL.md への反映
Step 4「fetch verify」セクションに以下を追記：
> ⚠️ timeout が出たら verify を**スキップ**して 30 秒以上待ち、次回ohayoで反映を確認する。同セッション内の即時再fetchはキャッシュの可能性があるため信頼しない。

## 教訓（短く）
- timeout = サーバ未到達ではない。**多くの場合は適用済み**
- 即リトライ禁止 → 燃費悪化＆同じエラーが連続
- セッション後半の notion-fetch は、セッション前半の更新が**反映されていることがある**（キャッシュ更新タイミング差）
