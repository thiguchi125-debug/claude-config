2026-08-26 構築。Google Drive の投函口を **マイドライブ直下に一本化**し、毎晩2:30に `_root_intake.py` が自動振り分けする仕組み。エンジン＝`~/.claude/agents/knowledge/kusagawa_archive/99_raw/_scripts/_root_intake.py`（旧 `_auto_intake.sh` から Phase 1 を交代・旧版は残置）。

**なぜ作ったか**：旧v4は `_INBOX_*` の**ファイル名キーワードだけ**で判定していたため、`スキャン_20260728-1901.pdf` のような手がかりの無い名前が判定不能のまま滞留した（構築時点で直下25件＋INBOX 14件＝39件）。しかも草川は実際には直下に置いていた＝ルール（直下禁止）と実態が乖離していた。**方針を実態に合わせて反転させた。**

**判定4段**：①安全ガード（フォルダ・更新10分以内・`.gscript` は触らない）②個人情報ガード（ファイル名に名簿/個人情報/連絡先/協力者→**中身を読まず** `00_名簿・個人情報/` へ）③ファイル名キーワード ④判定不能分だけ中身抽出→`claude -p` にバッチでJSON判定。確信度lowは `📥未分類_YYYY-MM/` へ（捨てない）。

**技術上の要点3つ**
- **スキャンPDFは画像だけでテキスト層が無い**（スマホの mlkit 製）。`pdftotext` は0文字を返す。`pdftoppm`+`tesseract -l jpn+eng` のOCRフォールバックが滞留解消の決め手。
- **議会資料の判定は STRONG／WEAK に分ける**。「予算書」「議事録」だけで議会送りにすると、地域団体の収支予算書や民間の打合せ議事録が議会アーカイブに紛れ込む（ドライランで実際に2件発生）。WEAK語は 亀山市/市議会/議会/市長/本会議 の文脈語を伴って初めて議会と確定する。
- **中身判定は個人情報がAIに渡ることを意味する**。ファイル名ガードで拾えるのは「名簿」等が名前に入っているものだけ。実際、構築時に `スキャン_20260728-1908.pdf`・`スキャン_20260801-1229.pdf` は中身を読んで初めて名簿と判明した。草川は承知の上でこの方式を選択。

**台帳**：全移動を `99_raw/_scripts/_intake_ledger.jsonl` に記録（元パス・先パス・判定根拠・判定者 rule/llm/guard/dedup/manual）。「あの資料どこ行った？」は [[project-smart-intake-drive-branch]] のモードB検索順5番目でここを見る。

**Claude Code経由の保存**：会話で「これDriveに保存して」。行き先が明快なら `--file <パス> --to <行き先>`、曖昧なら `--dry-run` で提案→承認→実行。行き先一覧は `--list-dests`（推測で打たない）。詳細は smart-intake SKILL.md の A-1b 節。

**朝の監視**：`_pipeline_status.json` の `root_intake_*` キーを ohayo が読む。旧v4キー（`council_moved` 等）はもう更新されない。
